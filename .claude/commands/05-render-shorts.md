STAGE 05 - RENDER, VERIFY. Follow CLAUDE.md §5, §7, §8 and `reference/qa-gates.md`. Video folder: `videos/<slug>/`. No paid calls here (voice spend happens only inside the ledger-gated adapter and only for a service the creator approved).
RESUME: a finished step whose inputs are unchanged is skipped; `python3 tools/pipeline.py status --project videos/<slug>` shows what is done and what is stale.

1. RUN THE PIPELINE at the output size (1920×1080 and 1080×1920 are the plan defaults; add `--fps 60` or set `config.fps` only if the creator asked for 60):
   `python3 tools/pipeline.py run --project videos/<slug> --auto-downgrade`
   Steps: validate → visuals → voice (stack from `--stack`, default `auto`: ElevenLabs only when a key is present and approved, otherwise the free local voice with a FALLBACK note) → assemble → align → Short audio (each Short assembled and aligned on its own audio) → plan → lint → mix (two-pass loudness) → render (H.264 yuv420p, BT.709, AAC) → captions → plan-aware allow-lists → media QA → motion QA → production report. Read the printed summary; do not paste it.
2. READ THE VERDICTS, per file, from `qa/<target>.json`, `qa/motion-<target>.json` and `review/production-report.md`. PASSED means no check found a defect, nothing more. FAILED names the cause and time range: fix the cause (scene data, asset, layout, voice take) and re-run; the pipeline redoes only what changed. BLOCKED means a measurement could not run or be trusted: fix the tool or report it; never treat it as a pass. At most 2 fix cycles per failing item. A failure you cannot fix is reported as FAILED with its cause; never edit a threshold, an allowance or the report to make a file pass.
3. LOOK where machines cannot: `qa/sheets/<target>/` (contact sheets), `render/previews/<target>/` (transition strips and clips), the first and last frame of each file, and for each Short frames at 0, 0.5 and 1.0 s (a legible subject, no black or empty opening). About 40 images in total. Write the findings to `qa/visual-review.md`.
4. PLAYBACK. `ffprobe` each file (the report already records size, codec, duration, bytes and sha256), confirm audio and video lengths agree, and play at least the opening, one transition and the ending of the long video and of one Short. The deliverables are `out/full-video.mp4`, `out/short-01.mp4` …, `out/captions.srt` (and `out/short-NN.srt`).
5. THUMBNAILS. `python3 tools/thumbnail.py --project videos/<slug> --text "<at most 3 words>" [--times t1,t2] --out out/thumbnail-1.jpg out/thumbnail-2.jpg …` builds honest thumbnails from the video's own frames (1280×720 JPEG under 2 MB, one headline of at most 3 words with measured contrast; checks are written to `review/thumbnails.json`). The promise must match the video. A Short's cover is its opening frame unless a better frame is chosen deliberately.
6. REPORT. `python3 tools/report.py --project videos/<slug>` (the pipeline already ran it) writes `review/production-report.md` and `.json`: verdict per file, transitions and downgrades, voice and alignment quality, spend per service, render timing, and **what a person still has to look at**. Do not summarise it more kindly than it reads.

EXIT CHECKS: every deliverable exists, is probed and has a QA verdict from this run · FAILED or BLOCKED items have a cause · thumbnails pass their checks · the report was regenerated after the last render.
